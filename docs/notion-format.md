# CGAI の Notion フォーマット（Claude と人の共通ルール）

> このファイルが Notion の書式の正本です。リポジトリの `docs/notion-format.md` と、
> ユーザーキットの `~/.claude/cgai/notion-format.md` は同じ内容にしておくこと（変えるときは両方）。

## 共通ルール
- すべてのページは CGAI トップページの下に作る。CGAI の外のページは読まない・作らない。
- 書き込む前に、作る・変える内容を利用者に見せて承認を得る。
- 人が書いた文章は消さない。直すときは追記・修正にとどめる。
- 他部署の人を @メンションしない。他部署のデータベースとリレーションを張らない。
- コードや会話から分からないことは推測で書かず【要記入】と残す。
- 実装の作業（ブランチ・PR 単位）は GitHub の Issue に置き、Notion には書かない。
- 全体データベースに書くときは、必ず「システム」プロパティを設定する（共通のものは空）。
- データベースの構造（プロパティの追加・削除・名前変更、リレーションの設定、ビュー）は変更しない。行（ページ）の追加と、本文・プロパティの値の記入だけを行う。構造の変更が必要だと思ったら、利用者に提案して環境管理者に依頼してもらう。

## 考え方
- システム固有のもの（仕様、利用者向けマニュアル）は、各システムの子ページに置く。
- 全体で参照したいもの（ナレッジ、現場の声・要望、議事録、障害記録、スケジュール）は、**CGAI 全体で1つのデータベース**に置き、各行に「システム」を付ける。システムページには、そのシステムで絞り込んだ「リンクドビュー」を埋め込む。
- 特定のシステムに属さないもの（チーム共通のナレッジ、全体の打ち合わせなど）は「システム」を空にする。
- 実装の作業（タスク）は GitHub の Issue に置く。全体の一覧は GitHub Projects の「CGAI タスク」で見る。Notion には書かない。

## ページの構成
```
CGAI（トップページ）
├── システム一覧（データベース）
│   └── {システム名}（システムページ）
│       ├── 仕様                  必須（子ページ）
│       ├── 利用者向けマニュアル    任意（子ページ）
│       └── 埋め込みビュー：ナレッジ / 現場の声・要望 / 議事録 / 障害記録 / スケジュール（このシステムで絞り込み）
├── ナレッジ（データベース）        全体共通
├── 現場の声・要望（データベース）   全体共通
├── 議事録・決定事項（データベース） 全体共通
├── 障害記録（データベース）        全体共通
└── スケジュール（データベース）    全体共通
```

## システム一覧（データベース）のプロパティ
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| システム名 | タイトル | 例: 売上集計ツール |
| 状態 | セレクト | 企画中 / 開発中 / 稼働中 / 停止予定 / 停止 |
| オーナー | ユーザー | 責任者1名 |
| GitHub | URL | リポジトリの URL |
| 現在のバージョン | テキスト | 例: v1.2.0 |
| 最終確認日 | 日付 | ページの内容が正しいと確認した日 |

## システムページの本文
```
# {システム名}
## 概要
{何をするシステムか。誰が使うか。3行以内}
## 動かし方
### 開発環境での起動
### 現場への反映（リリース）
### 問題があったときの戻し方
## 担当者
- オーナー：
- 連絡先：
## 変更履歴
| バージョン | 日付 | 主な変更 |
## リンク
- 仕様：（子ページ）
- GitHub：
## このシステムの記録
（ナレッジ / 現場の声・要望 / 議事録 / 障害記録 / スケジュールの、このシステムで絞り込んだビュー）
```
リリースのたびに「変更履歴」に1行追記し、プロパティの「現在のバージョン」を更新する。
「このシステムの記録」の絞り込みビューは、Claude からは作れないことがある。その場合は見出しだけ作り、利用者に「Notion で開いてビューを追加（またはテンプレートを適用）してください」と伝える。

## 仕様ページ（子ページ、タイトル「仕様」）
```
# 仕様
## 1. 目的
## 2. 使う人と場面
## 3. やりたいこと（箇条書き）
## 4. 入力と出力（入力 / 出力 / 画面）
## 5. 条件（動かす環境 / 扱うデータ / その他）
## 6. 完了条件
## 未決事項
## 仕様の変更履歴
| 日付 | 変更内容 | 理由 | 変更した人 |
```
- 各項目は箇条書き1〜2行で十分。
- 仕様を変えたら必ず「仕様の変更履歴」に1行追記する（Claude が変えたときは「変更した人: Claude」）。
- 「扱うデータ」に個人情報・顧客情報が含まれる場合は必ず明記する。

## 利用者向けマニュアル（子ページ）
```
# 利用者向けマニュアル
## できること（3行以内）
## 準備（インストール・初回設定）
## 使い方（手順を番号付きで）
## よくある質問
## 困ったときの連絡先
```
現場の人が読む前提で、専門用語を使わずに書く。

## ナレッジ（全体データベース）
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| タイトル | タイトル | 例: Shift_JIS の CSV で文字化けする |
| システム | リレーション（複数可） | 関係するシステム。共通の知識なら空 |
| 分類 | セレクト | 現場 PC・環境 / データ・ファイル / ライブラリ・言語 / GitHub・Claude の使い方 / 業務知識 / その他 |
| 記録日 | 作成日時 | 自動 |
| 記録した人 | テキスト | 名前、または Claude |
本文:
```
- 起きたこと：
- 原因：
- 解決策：
- 関連 Issue / PR：
```
ビュー: 新しい順（全体）/ 分類別 / 各システム（システムページに埋め込み）

## 現場の声・要望（全体データベース）
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| 内容 | タイトル | 1件1行 |
| システム | リレーション | 対象のシステム。新しいシステムの要望なら空 |
| 受けた日 | 日付 | |
| 誰から | テキスト | 部署・名前 |
| 状態 | セレクト | 未対応 / 検討中 / 仕様に反映 / 対応済み / 見送り |
| Issue 番号 | テキスト | 例: csv-export-tool#12 |
ビュー: 未対応（全体）/ 各システム（埋め込み）。システムが空の要望は、新しいシステムの種になる。

## 議事録・決定事項（全体データベース）
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| 会議名 | タイトル | 例: 現場ヒアリング（経理部） |
| 日付 | 日付 | |
| システム | リレーション（複数可） | 関係するシステム。全体の打ち合わせなら空 |
| 参加者 | テキスト | |
本文:
```
- 話したこと：
- 決めたこと（と理由）：
- 次にやること（誰が・いつまで）：
```
決めたことが仕様に関わる場合は、仕様ページにも反映する。

## 障害記録（全体データベース）
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| 何が起きたか | タイトル | |
| システム | リレーション | |
| 発生日 | 日付 | |
| 影響 | セレクト | 大（業務が止まった）/ 中（回避策あり）/ 小 |
| 状態 | セレクト | 対応中 / 復旧済み / 再発防止済み |
本文:
```
- 影響（誰が・何に困ったか）：
- 原因：
- 対処（戻したバージョン、修正した Issue）：
- 再発防止：
```

## スケジュール（全体データベース）
| プロパティ | 種類 | 値 |
| --- | --- | --- |
| 予定 | タイトル | 例: 現場ヒアリング、試験版を現場で試す、v1.0 リリース |
| システム | リレーション | システム一覧の該当システム（全体の予定なら空） |
| 種類 | セレクト | ヒアリング / 開発 / 現場試験 / リリース / その他 |
| 期間 | 日付（開始〜終了） | |
| 担当 | ユーザー | |
| 状態 | ステータス | 未着手 / 進行中 / 完了 |
| 関連 Issue | テキスト | 開発の予定のときだけ（例: csv-export-tool#3〜#5） |
- 1行は半日〜数日の大きさ。実装の細かい作業は書かず、「開発（#3〜#5）」のようにまとめる。
- ビュー: 全体タイムライン（システムでグループ化）/ 今週・来週（表）/ 各システムの予定（埋め込み）

## タスク（GitHub）
- 実装の作業は各リポジトリの Issue。システムに属さないチームの作業（購入手続き、現場との調整など）は `cgai-team` リポジトリの Issue にする。
- 全体の一覧は GitHub Projects の組織プロジェクト「CGAI タスク」。CGAI の全リポジトリの Issue が自動で追加される。
- Notion にタスクを書き写さない。スケジュールから Issue 番号で参照する。
